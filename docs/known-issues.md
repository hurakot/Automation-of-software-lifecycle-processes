# Ограничения и планы

Описание текущей реализации; перечисленные улучшения пока не реализованы.

## Безопасность

- Нет CSRF-защиты у POST-форм, включая вход, создание, запись и выход. Подключить CSRF-токены с серверной проверкой.
- Нет rate limit и требований к длине/сложности пароля. Регистрация открыта всем.
- Роль при записи читается напрямую: пользователь может отправить произвольную роль, включая `organizer`. Добавить whitelist `participant/speaker` и проверку обязательной темы для `speaker` на сервере.
- Ошибки регистрации и записи выводятся через `flash(str(e))`; `/health` также возвращает текст исключения БД. Заменить общими сообщениями и внутренним логированием.
- Не заданы production-политики cookie `Secure` и `SameSite`; параметры надо явно согласовать с HTTPS и CSRF-защитой.
- `SECRET_KEY` обязателен в окружении, но пустая или слабая строка не отвергается отдельной проверкой.
- В Dockerfile нет `USER`: приложение работает от root. Добавить непривилегированного пользователя с подходящими правами.
- Порт `8000:5000` во всех Compose открыт на всех интерфейсах. Для nginx на хосте привязать к `127.0.0.1`; Docker-публикации нельзя считать защищёнными только настройкой ufw.

## Валидация и целостность

- Валидация в основном браузерная. Нет серверной проверки порядка дат, неотрицательного взноса, пустых строк и формата телефона. Ограничение NOT NULL не запрещает пустую строку.
- Уникальность названия конференции проверяется только перед вставкой; параллельные запросы могут создать дубли. При таком бизнес-требовании добавить UNIQUE миграцией и обработку конфликта.
- В БД отсутствуют CHECK для ролей и форматов. Создание конференции нормализует неизвестный формат в `offline`, запись роль не нормализует.
- Уникальная пара пользователь–конференция защищена БД, но конфликт конкурентных записей попадает в общий обработчик исключений.

## API и возможности интерфейса

- Приложение обслуживает HTML-формы, не предоставляет полноценный JSON API и OpenAPI.
- Бизнес-ошибки часто возвращают `200` с flash или `302`, а не отдельный HTTP-код ошибки.
- Нет редактирования/удаления конференций, отмены участия, управления участниками, восстановления пароля и админ-панели.
- `fee` хранится числом, но оплаты и платёжной интеграции нет.
- Формат `online` не создаёт видеовстречу; отдельного поля ссылки подключения нет.
- Нет фильтров и поиска. Сортировка по одинаковой `start_date` не имеет дополнительного стабильного ключа.
- После входа всегда открывается главная, исходная защищённая страница не восстанавливается.

## Архитектура

- Настройки, обработчики и бизнес-логика сосредоточены в `app.py`. Разделить на фабрику приложения, blueprints и сервисы при росте проекта.
- Часть импортов и зависимостей не используется основным сценарием; `1.py`, `hello.py`, `good.txt` — вспомогательные файлы.
- Используются устаревающие формы ORM Query API, например `Conference.query.get`; постепенно перейти на `db.session.get` и SQLAlchemy select.
- ORM-каскад не эквивалентен SQL `ON DELETE CASCADE`: прямое удаление SQL требует отдельного рассмотрения связей.

## Эксплуатация

- В каждом web-контейнере перед стартом выполняется миграция. При масштабировании несколько контейнеров могут запустить её одновременно: выделить один migration job.
- Индекс создаётся вне транзакции через `CONCURRENTLY`; после частичного сбоя проверить индекс и Alembic-состояние, а не считать всю ревизию автоматически откатившейся.
- PostgreSQL healthcheck проверяет готовность подключений. `/health` выполняет только `SELECT 1`, а не проверку прикладной схемы.
- У `web` нет Docker healthcheck; `depends_on` не обеспечивает автоматическое восстановление приложения после любого сбоя БД.
- Фиксированные имена `conf_db/conf_web` и порт конфликтуют между стендами на одном хосте.
- Секреты и данные сохраняются локально; шифрование/внешнее хранилище бэкапов и расписание в репозитории не настроены.
- `dbtools.sh` не включает строгую проверку ошибок всех команд конвейера. `compare` подтверждает наличие CREATE TABLE, `backup` проверяет COPY, но это не заменяет пробное восстановление.
- TeamCity-конфигурации как код отсутствуют: порядок шагов, ветки, триггеры и реквизиты registry нужно восстанавливать из настроек сервера.
- Отчёты CI и cookie-файлы не перечислены в текущем `.gitignore`; не добавлять их в коммиты.

## Приоритет улучшений

1. Серверная валидация ролей/полей, CSRF, безопасные сообщения ошибок.
2. Production-настройки cookie, ограничение входа, непривилегированный контейнер.
3. Отдельный migration job, проверка восстановления бэкапа и версионируемый pipeline.
4. Разделение монолита, редактирование конференций и отмена участия.

Порядок запуска и восстановления — в [deployment.md](deployment.md); тесты текущего поведения — в [development.md](development.md).
